# Zotero 访问层与故障排查

> **工具本体、完整参数表、每个子命令的输入输出**：[tools/zotero/README.md](../tools/zotero/README.md)。
> 本文讲**为什么这么设计、坑在哪、坏了怎么查**——即「原理与排错」。
> 相关：[02-quickstart.md](02-quickstart.md)（先跑通）｜[03-workflow.md](03-workflow.md)（批注在流程里的位置）｜[06-agent-integration.md](06-agent-integration.md)（Agent 怎么调）｜[07-faq.md](07-faq.md)。

## 结论先行

1. **这一层是只读的。** 它从不写 Zotero——不改条目、不改批注、不建集合。Zotero 是**不可变源**，工具只负责把它读准。
2. **默认就是全量。** `annotations` / `children` / `collections` / `tags` / `searches` 不传 `--limit` 时都翻完全部分页、输出全部命中。批注就是证据层本身，最大的坑不能留在默认路径上。
3. **有 7 个坑，全部是 Zotero Local API 的真实行为**，不是本工具的 bug。工具或绕开、或如实报告，但**你必须知道它们存在**——否则会拿到一份「看起来正常、其实是残缺」的读数。
4. **凡是「返回的比存在的少」，输出里必须显式说出来**（`truncated` / `matchedTotal` / `scanned` / `warning` / `note`）。看到这些字段空着才等于「确实是全部」。

# 1. 这一层是什么

`tools/zotero/rvzotero.py` 是一个**单文件、纯 Python 3.8+ 标准库、只读**的 CLI，把 Zotero 桌面版的 Local API 包成一组稳定子命令。

| 属性 | 取值 |
|---|---|
| 依赖 | **无**。只用标准库（`urllib` / `json` / `argparse` / `http.server`） |
| 方向 | **只读**。只发 GET，没有任何写路径 |
| 目标 | Zotero 桌面版**本地** API（不是 Web API，不需要 API key、不需要联网） |
| 前置 | Zotero 正在运行，且已在设置里**允许其他应用与 Zotero 通信** |
| 输出 | 默认 JSON（UTF-8、`ensure_ascii=False`）；`--human` 给人类可读表格 |

它存在的理由是**把「读 Zotero」这件事从「每次重新踩坑」变成「一次踩完、写进代码」**。同一个逻辑被 Agent 反复手写时，最容易丢的恰恰是下面第 4 节那 7 个坑中的某一个——而丢一个坑的后果是**数据静默残缺**，不是报错。

**「只读」的边界是硬约束**：本工具、本文档、以及任何基于它写的 Agent 流程，都不得以任何方式写入 Zotero。需要改 Zotero 时，由**研究者本人在 Zotero 里改**。

## 为什么走 Local API，而不是依赖第三方插件

| | Local API + 本工具 | 依赖第三方插件 |
|---|---|---|
| 依赖 | 无。Local API 是 Zotero 自带的 | 插件装没装、版本对不对、有没有被禁用 |
| 可移植 | 一份 `rvzotero.py`，`git clone` 下来就能跑 | 每个使用者都得先装同一个插件 |
| 可验证 | HTTP 行为可 mock、可离线单测 | 插件内部行为是黑盒 |
| 行为边界 | 坑是**确定的**，写进代码一次解决 | 坑随插件版本漂移 |
| 失败模式 | 退出码 + stderr 修复步骤 | 「读出来是空的」，看不出为什么 |

关键的差别在最后一行：**插件读不到东西时，你分不清「这篇论文没有批注」和「插件坏了」**。本工具把「找不到」（退出码 `5`）与「读取失败」（`3` / `4`）拆成不同退出码，并在每一处截断都显式报告。

# 2. 配置：四个口子

命令行开关优先于环境变量，环境变量优先于内置默认值。

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `RV_ZOTERO_API` | `http://127.0.0.1:23119/api` | Local API 基址。端口被占用或改过时用它覆盖 |
| `RV_ZOTERO_LIBRARY` | `users/0` | 库标识。`users/0` 是「当前登录用户」的别名，本机自用就够了 |
| `RV_ZOTERO_STORAGE` | 平台默认 | 直接指定 Zotero 的 `storage/` 目录 |
| `RV_ZOTERO_DATA_DIR` | 平台默认 | 指定 Zotero **数据目录**，工具自动接上 `storage` |

## 怎么开启「允许其他应用与 Zotero 通信」

Zotero → **设置** → **高级** → 勾选 **「允许其他应用与 Zotero 通信」**
（英文界面：Settings → Advanced → *Allow other applications on this computer to communicate with Zotero*）。

不开这个开关，Local API 根本不起监听，所有子命令都会以退出码 `3` 失败——而端口连不上这一点**从报错里看不出来**是权限问题，所以这是「连不上」的第一嫌疑。

改完不需要重启 Zotero；`ping` 立刻能验证：

```bash
python tools/zotero/rvzotero.py ping
```

**Zotero 数据目录在哪**：Zotero → 设置 → 高级 → 文件和文件夹，里面写着「数据目录位置」。

附件路径解析（`attachment` 子命令）在拿不到磁盘路径时会返回 `exists: false` 与 `linkMode`，**不会编一个看起来像真的路径给你**。网页附件（`linked_url`）磁盘上本来就没有文件，工具明确返回「没有路径」而不是猜。

# 3. 退出码

退出码是这一层与调用方之间的**契约**——不要只看 stdout 有没有内容。

| 码 | 含义 | 调用方该做什么 |
|---|---|---|
| `0` | 成功 | 正常消费输出 |
| `2` | 参数错误 | 调用方写错了。**不要重试**，去看 stderr 的提示改参数 |
| `3` | 连不上 Zotero | 环境问题。stderr 里有可照着做的修复步骤；修好再重试 |
| `4` | Zotero 回了非 200 | 多半是端点用法不对；把 stderr 里的状态码与响应体一起报上来 |
| `5` | 未找到 | key 不存在，或该条目没有这类子对象。**这是正常的「没有」，不是故障** |

`5` 值得单独强调：**「找不到」和「读取失败」必须能分开**，否则「这篇论文没有批注」和「我读批注读挂了」会混成同一件事，而这两件事对下游的含义完全相反。

# 4. 七个坑

下面每一条都是**在真实 Zotero 上实测出来的行为**。工具已经处理，但你得知道它们存在——因为手动调 API、或换一个工具时，它们会原样回来。

## ① 裸 `/children` 会静默漏掉全部批注

`GET /items/<key>/children`（不带参数）**不给批注**，而且**不报错**：

| 调法 | 真实返回 |
|---|---|
| `/items/<条目KEY>/children` | 直接子对象：附件、笔记。**批注 0 条** |
| `/items/<附件KEY>/children` | **空数组**（连批注都不给） |
| `/items/<条目KEY>/children?itemType=annotation` | 该条目**所有附件**上的批注（真机实测 130 条） |
| `/items/<附件KEY>/children?itemType=annotation` | 该附件自己的批注（130 / 0） |

原因：Zotero 把批注存成 **PDF 附件的子对象**，不是论文条目的直接子对象。裸 `/children` 返回的是直接子对象——两个附件，仅此而已。

**处理**：**读批注的首选入口是 `annotations --key <KEY>`**——它给全量、带颜色过滤、带 `🔤` 区间切分、带 Zotero 官方页码标签，是这一层唯一从头到尾为批注设计的子命令。

`children --include annotations`（注意 **`--include` 只认复数**）在真实 API 上**同样有效**，条目级 `itemType=annotation` 过滤会跨附件聚合；它适合「一次把附件 + 笔记 + 批注的条数都看一眼」，不适合做证据读取。两条路都能走通，不存在「`children` 拿不到批注」这回事。

> 早期版本的 `children --help` 把 `--include` 的取值印成单数 `attachment,note,annotation`，与实现相反（实现只认复数）。**这是过去时，现已修正**——帮助文本与实现一致，传单数会明确报错并提示改成复数。

**怎么确认自己没踩**：如果一篇你明明画满高亮的论文读出「0 条批注」，先看你用的是哪条路——裸 `/children` 必然是 0。

## ② 批注在 100 条处静默截断

`?itemType=annotation` **单页最多 100 条**，传 `limit=1000` 也没用。请求 130 条会**安安静静地只给你 100 条**，HTTP 200，没有警告。

**唯一可靠的条数**是 `Total-Results` 响应头——不是数组长度。

**处理**：`annotations` 默认 `start` 翻页取全量；`children` 默认也翻完全部页。只有你**显式**传 `--limit` 时才会撞上单页上限，此时输出里会出现 `warning` + 真实的 `total`。

**怎么确认自己没踩**：比对 `total` 与 `Total-Results`。或者更省事——**看到条数正好是 100、200、300 这种整数就怀疑截断**。真实批注数很少正好卡在整百。

## ③ Local API 回 HTTP/1.0

Zotero Local API 的响应是 **HTTP/1.0**。Python `urllib` 正常；**PowerShell 的 `Invoke-RestMethod` / `Invoke-WebRequest` 会握手失败**，而且报的错通常看不出跟协议版本有关。

**处理**：用本工具，或 `curl.exe -o` 落盘后用 Python 读。**不要在 PowerShell 里解析这个 API 的 JSON。**

这条也是 Windows 上「浏览器能打开 `/api/users/0/items`，但脚本说连不上」的**首要嫌疑**——浏览器容忍，PowerShell 不容忍。

## ④ 批注可能只挂在**某一个**附件上

一篇论文常有多个 PDF 附件：原文一份、双语对照一份、机器译文一份。**批注只落在研究者实际阅读的那一份上**——可能是译文，也可能只是原文。

只查「第一个附件」或「主附件」，会得到 0 条或残缺的结果，而且没有任何报错。

**处理**：`annotations` 默认**逐个附件都查**再合并；`--first-attachment` 才是「只查一个」的显式降级。

## ⑤ 父条目查询是递归的，会和逐附件查询重复

`/items/<父条目>/children?itemType=annotation` **会递归返回其所有附件下的批注**。所以「逐附件查一遍」+「父条目查一遍」会把同一批批注拿两遍——实测某条目真实 130 条，两路相加报出 **260 条**。

**处理**：工具在合并后**按 key 去重**，并在输出里给 `deduped` 与 `dedupeNote`。注意 `attachments` 各行是**去重前**的分项读数，**相加会大于总数**——这是刻意的：分项读数用于定位「批注落在哪个附件上」，总数以去重后的为准。

**顺带一个直觉纠正**：坑 ④ 和坑 ⑤ 并不矛盾。**两条路径互补**——父条目递归查询能一次拿到全部批注（省请求），逐附件查询能告诉你每条批注属于哪个文件。工具两条都走，然后去重。

## ⑥ `/fulltext` 会静默忽略 `?page=N`

给 `/items/<附件key>/fulltext` 传任何页码，返回的都是**整篇**——传 `page=1`、`page=27`、`page=999` 拿到的字节完全相同。返回体里有 `totalPages`（真实总页数），但**没有逐页边界**。

后果很实在：想逐页取全文，等于把同一篇 200KB+ 的全文**重复下载 N 遍**。

**处理**：工具**只请求一次**，拿回整篇后**在本地**按字符偏移估算页边界。

> **页码纪律**：这样切出来的页码是**估算值**，输出里一律带 `pageEstimated: true` / `pageSource: "local_char_offset_slice"`，与批注的 `annotationPageLabel`（Zotero 官方标注）在字段层面就分得开。**引用页码时请用批注的页码**，不要用全文切分的估算页码。
>
> `fulltext` 因此**不再接受按页请求**：`--page N` 已移除，只有 `--pages A-B`（本地切分）。

## ⑦ 颜色过滤 × 条数上限会互相干扰

如果实现是「数够 N 条就停」，那么 `--color purple` 只会扫前几页，然后报告一个**假的小数字**——你会以为紫色批注只有几条，实际上只是没扫到。

**正确顺序**：**先全量分页扫完 → 再按颜色过滤 → 最后才按 `--limit` 截断输出**。工具按此实现，并且把每一步的数字都报出来（`scanned` / `matchedTotal` / `total`）。

同理，`tags -q` 的过滤也是**在整套分页之上**做的，不是「只在第一页里找」。

# 5. 「返回的比存在的少」必须说出来

这是整套工具最重要的一条输出纪律：**静默截断是这套工作流最大的敌人。**

| 字段 | 含义 | 什么时候出现 |
|---|---|---|
| `total` | 本次**实际返回**的条数 | 列表型子命令都有 |
| `matchedTotal` | 过滤条件**命中**的总条数（已扫描到的） | 有过滤或截断时 |
| `scanned` | 为得到上面的数字**实际扫过**多少条 | 有过滤或截断时 |
| `pages` | 翻了几个分页 | 全量分页的子命令 |
| `truncated` | 是否**因为你传了 `--limit`** 而少给 | 只有显式上限时才可能为 `true` |
| `deduped` | 因父子递归重复而合并掉的条数 | 批注查询 |
| `note` | 人类可读的说明（截断原因、改法） | 需要解释时 |
| `warning` | 需要使用者注意的行为（如撞上单页上限） | 命中异常行为时 |

**判据**：`total < matchedTotal` 就是「少给了」，此时必然有 `truncated` 或 `warning` 解释原因。**如果三者都空着，你拿到的就是全部**——这是可以依赖的不变量。

Agent 侧的对等要求：**不要看到数组非空就当作读全了**。先看 `truncated`。

## 5.1 全文检索的片段也要算这笔账

`retrieve` 把整篇全文切成片段再做 BM25，这条链路上同样有「切出来的比拿到的少」：

| 字段 | 含义 |
|---|---|
| `rawPassages` | 第一层切分切出多少段（还没合并、没过滤） |
| `mergedPassageCount` | 短片段向后合并后剩多少段 |
| `passageCount` | **最终参与检索**的片段数 |
| `keptChars` | 最终保住的字符数 |
| `droppedPassages` / `droppedChars` | 被丢弃的段数与字符数（必须能对上账） |
| `minCharsUsed` / `cjkMinChars` | 本篇实际用的长度门槛（拉丁 / CJK） |
| `cjkHeavy` | 本篇是否以 CJK 为主 |
| `matched` / `returned` | BM25 命中多少段 / 实际返回几条 |

**片段长度门槛不是「短了就扔」**：短片段**先向后合并**（合并上界 700 字符），合并不掉的仍然保留。只有整段不含任何字母/数字/CJK 的**排版残留**（表格线、分隔符）才会被丢弃，而丢了多少一定记在 `droppedPassages` / `droppedChars` 里。

**CJK 门槛单独算**：中文一个字就是一个词，拿拉丁文本的 60 字符门槛卡中文，会把完全正常的段落判成碎片。所以 CJK 占比高的片段门槛降到 **20 字符**（拉丁仍为 60）。门槛按**每个片段自己**的脚本判定，不按整篇——中英混排的论文里，中文段落照样享受低门槛。

> **这条纪律的来由（真实教训）**：早期实现在「切出多于 3 段」时会把所有短于门槛的片段**整块丢掉，一个字都不报**。真机复测那份 245167 字符的中文 PDF：原始切出 **4526** 段，旧实现只留下 **1763** 段——**2763 段（61%）无声消失**，其中就包括被切成 20–40 字的中文短句。同一篇文件改成「先合并、后过滤、丢弃记账」之后，**0 段被丢弃**，`keptChars` 242973 / 245167（99.1%）。
>
> 这个缺陷在离线测试里**没有被发现**，因为当时仅有的两个切分测试恰好都落在「片段数 ≤ 3」的直通分支上——分支没被覆盖，路径就不会暴露。现在有专门的回归测试锁死「合并 / 过滤」分支必须真的被执行。

**`passages == 0` 时必须说清是哪种 0**：

| 情形 | 输出 |
|---|---|
| 附件根本没被索引，全文 0 字符 | `warning`：「Zotero 返回的全文是空的……这是『没有可检索内容』，不是检索词的问题」 |
| 全文非空，但切分/过滤后 0 片段 | `warning`：「这是**切分后为空**，不等于全文里没有内容」+ 丢弃计数 |
| 全文有片段，但没有一个命中检索词 | `matchNote`：「已检索 N 个片段……**确实没有**匹配——这是『确实没有』，不是『没检索到』」 |

三种情况的下一步动作完全不同，所以不能都归成「返回 0 条」。

# 6. 页码：官方标注 vs 估算

这是最容易被误用的一处，工具在输出里**强制区分**：

| 来源 | 字段 | 可信度 | 用在哪 |
|---|---|---|---|
| Zotero **官方**批注页码标签 | `annotationPageLabel`（输出里也叫 `page`） | **权威**。就是 Zotero 界面上显示的那个页码 | 引用、证据对象里的 `(页码)` |
| 全文按字符偏移**估算** | 估算 `page` + `pageEstimated: true` + `pageSource: "char_offset_estimate"` | **估算**。误差随排版、图表、参考文献而变 | 只用来定位「大概在哪」，不进正式引用 |

**为什么必须有这个区分**：`(页码)` 是要写进论文笔记、甚至写进论文的。估算页码混进引用，就等于给证据标了一个**看起来精确、实际可能是错的**位置。批注页码是研究者自己点出来的，它才是权威。

`retrieve`（全文 BM25 检索）返回的每条结果都带 `pageEstimated: true` 与 `charOffset`；它的 `note` 会明说「需要精确页码请改用 `annotations`」。

# 7. 评论归属：按 `🔤` 区间切分

Zotero 的批注评论字段里混着**两种来源完全不同的文本**：

```
🔤机器译文🔤
研究者手写的话
```

翻译插件给它自己生成的文本套上 `🔤…🔤` 标记，标记**外面**的才是研究者本人写的。

**切分必须按区间做，不能按「整条含不含 `🔤`」判断。** 上面这条评论整条都含 `🔤`，但研究者那句话在区间外——按整条判断就会把**研究者的话当成机器产物丢掉**，那正是证据层最不该丢的东西。

工具输出 `commentParts`，其中 `classification` 四种取值：

| `classification` | 含义 |
|---|---|
| `tool_generated` | 整条都是机器译文（`🔤…🔤` 区间外没有别的字） |
| `machine_plus_researcher` | 机器译文 + 研究者的话**都有**，已分开 |
| `researcher` | **没有 `🔤` 标记 = 研究者手写的**（翻译插件只给自己生成的文本加标记） |
| `mixed` | 少见形态：没切分过，标记与区间外文本同时存在 |

**要研究者本人的话，就取 `researcher_comment`（等价于 `researcher_text` 或 `unmarked_text`）。** 机器译文**永不作论文原文**，也不进证据层。

空评论同样归为 `researcher`（没有机器标记），此时 `researcher_comment` 是空串——**不要用 `classification` 判断「有没有话」，要用 `researcher_comment` 是否为空**。

`raw` 始终保留原样，便于回溯。

# 8. 与 ingest 流程的接口

批注是**证据层**的原料。颜色决定它流向哪里（与 `ResearchVault/00_System/AGENTS.md` 的五色通道一致）：

| 颜色 | 十六进制 | 含义 | 流向 |
|---|---|---|---|
| 🟡 yellow | `#ffd400` | 生词 | `03_Vocabulary/`（**不进证据、不进 Wiki**） |
| 🟢 green | `#5fb236` | 定义术语或术语解释 | `E` 对象 → concept 页 |
| 🔵 blue | `#2ea8e5` | 影响、观点、解决方法 | `E` 对象 → 主张登记表 |
| 🔴 red | `#ff6666` | 缺陷、现有问题、现有挑战 | `−` 证据 / `gap/` |
| 🟣 purple | `#a28ae5` | 与我的研究相关 | `§7 研究关系` / `research_position` 首要依据 |

取批注的标准做法——**首选入口就是 `annotations --key <KEY>`**：

```bash
# 全量（默认行为）；--split-comment 顺带把机器译文与研究者的话分开
python tools/zotero/rvzotero.py annotations --key ABCD1234 --split-comment

# 只看某一色（先全量扫描再过滤，不会假阴性）
python tools/zotero/rvzotero.py annotations --key ABCD1234 --color purple
```

选它的理由：**给全量、带颜色过滤、带 `🔤` 区间切分、带 Zotero 官方页码标签**，输出里还带 `matchedTotal` / `scanned` / `deduped` 这些如实读数。它是这一层唯一从头到尾为批注设计的子命令。

`children --include annotations`（**只认复数**）在真实 API 上**也有效**，条目级过滤会跨附件聚合，输出是每一类子对象的**条数**。它适合快速盘一遍「这篇有几个附件、几条笔记、几条批注」，**不适合**做证据读取——没有颜色过滤、没有评论切分、没有页码标签。

**三条流程纪律**：

1. **逐附件取全**（坑 ④），不要只查一个 PDF——工具默认就是这么做的。
2. **条数接近或等于 100 时必须分页补齐**（坑 ②）。工具默认已补齐；**手动调 API 时这一步必须自己写**。
3. **引用的页码用 `annotationPageLabel`**，不要用全文估算页码（第 6 节）。

# 9. 离线自测

测试**不依赖 Zotero 运行**——`tests/mock_zotero.py` 起一个标准库 HTTP 服务，复现上述全部真实行为（HTTP/1.0、`Total-Results` 头、裸 `/children` 返回 0 条批注、100 条截断、`?page=N` 被忽略、批注只挂一个附件、`🔤` 评论）：

```bash
cd tools/zotero
python tests/test_rvzotero.py          # 全绿 = 访问层行为未被改坏

# 想手动看假数据长什么样
python tests/mock_zotero.py 23199
python rvzotero.py --api http://127.0.0.1:23199/api ping
```

测试里刻意断言了几个「反直觉但真实」的行为，改代码时别把它们「修正」掉：

- 裸 `/children` 必须返回 **0 条批注**（这是真实行为，不是 bug）；附件 key 的裸 `/children` 回**空数组**；
- **条目 key** 的 `?itemType=annotation` 必须**跨附件聚合**（真机实测 130 条），而**附件 key** 只回它自己的批注；
- 批注总数必须是 **130 而不是 100**（分页补齐）；
- `🔤…🔤\n研究者的话` 必须切出**两段**，研究者的话不能丢；
- 任何非空全文切分后 `keptChars` 必须 **> 0**（不存在「有内容却 0 片段」）；
- 「合并 / 过滤」分支必须**真的被执行**（别又落回小样本的直通分支——那正是这条缺陷当年漏网的原因）；
- 连不上 Zotero 必须退出码 `3`，且 stderr 里要有**可执行**的修复步骤。

> **mock 的边界（重要）**：mock 只能验证「工具在 mock 建模的世界里自洽」，**不能**验证工具与真实 API 一致。这个项目已经因此吃过一次亏——mock 曾把「条目级 `itemType=annotation` 只对附件 key 生效」钉死，于是离线全绿、真机结论相反，差点把一个**正确的实现**当成 blocker 改坏。
>
> 所以：`tests/mock_zotero.py` 顶部的语义**以真实 Zotero 实测为准**，文本里写了「改动前请先在真机复核」。**凡是对真实外部接口的断言，先在真机上跑一遍；mock 与真机不一致时，先怀疑 mock。**

# 10. 排错对照表

| 现象 | 大概是什么 | 怎么办 |
|---|---|---|
| 退出码 `3`，提示连不上 | Zotero 没开 / 本地 API 没开 / 端口不对 | 打开 Zotero；设置 → 高级 → 允许其他应用与 Zotero 通信；`ping` 复测 |
| 浏览器能开、PowerShell 连不上 | **HTTP/1.0**（坑 ③） | 改用本工具或 `curl.exe`；别用 `Invoke-RestMethod` |
| 批注读出 0 条，但论文上明明有高亮 | 裸 `/children`（坑 ①）／只查了第一个附件（坑 ④） | 用 `annotations`（默认逐附件 + 显式 `itemType=annotation`） |
| 批注条数正好是 100 / 200 | 单页静默截断（坑 ②） | 用 `annotations`；看 `total` 与 `Total-Results` |
| 批注条数比预期多一倍 | 父条目递归 + 逐附件重复（坑 ⑤） | 看 `deduped` / `dedupeNote`；总数以去重后为准 |
| 紫色批注只读出几条 | 颜色过滤撞上条数上限（坑 ⑦） | 用 `annotations`（先全量扫描再过滤），检查 `scanned` |
| 全文里找不到某段 | 该 PDF 没被 Zotero 索引 | 先看 `fulltext` 的 `indexedPages` / `totalPages`；未索引的附件是**已知缺口**，不是「没有内容」 |
| `attachment` 返回 `exists: false` | 附件没下载到本地 / 是网页附件 | 在 Zotero 里下载该附件；`linked_url` 磁盘上本来就没有文件 |
| 中文输出乱码 | Windows 控制台编码 | 工具已显式把 stdout 切到 UTF-8；若仍乱码，设 `PYTHONIOENCODING=utf-8` |
| 退出码 `5` | key 不存在，或该条目确实没有这类子对象 | **这是正常的「没有」**，按「无批注」处理，别当故障重试 |
| 退出码 `4` | 端点用法不对 | 把 stderr 里的状态码与响应体一起报上来 |
| `--include` 报参数错 | 写了单数 | 用复数：`attachments,notes,annotations`（报错里会给出正确写法） |

# 11. 边界：这一层**不**做什么

- **不写 Zotero**。任何写操作都由研究者在 Zotero 里自己做。
- **不联网**。只与本机 Local API 通信；不需要 API key，也不该有。
- **不引入第三方依赖**。纯标准库，`git clone` 下来就能跑。
- **不做完整 CSL 排版**。`export ... citation` 只给 APA / IEEE / GB-T-7714 的**近似**格式，够看、够粗排；正式引用请用 Zotero 自己的样式引擎，或 `bibtex` / `csljson` 交给外部工具。
- **不把估算当权威**。页码、切分、去重都带来源标记；分不清来源的读数不允许进入证据层。
- **不搬运 PDF**。附件只解析路径，不复制、不改名——PDF 不进 Vault。
